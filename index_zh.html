UX 案例研究 · Claude Code · 2026

修复 /btw 中不可见的状态边界

Claude Code 的 /btw 命令会创建临时侧边对话。关闭浮层后，回答永久消失——没有警告，没有恢复路径。我识别了这个设计缺陷，向 Anthropic 提交了核心修复提案，并以插件形式完成了一个可运行的替代方案。

01 — 问题

回答消失了。
没有警告，没有恢复。

这个问题是我在使用 Claude Code 时亲身遇到的。我用 /btw 提了一个问题，得到了有用的回答，按下 Escape——回答就消失了。我的第一反应是：这是 bug 吗？

在调查架构之后，我确认这是刻意的设计。但无论设计意图如何，这个时刻的用户体验是断裂的。

Claude Code — 用户旅程还原
用户 /btw 你喜欢多模型方案吗？比如 deepseek + claude？
claude 多模型方案在架构上是合理的。DeepSeek 在成本效益
上表现突出；Claude 在安全性和指令遵循上有优势…
用户 [按下 Escape]
回答永久消失——没有任何提示。

根本原因：浮层的外观和交互感与普通 Claude 回答完全一致。没有任何视觉线索区分"临时内容"与"持久内容"。这直接对应 Nielsen 可用性启发式第一条——系统状态的可见性。

受影响的用户群体

①
Claude Code 新用户

尚未理解 /btw 的临时性本质。每一条回答看起来都一样——没有"这条会消失"的心智模型。

②
深度专注工作中的开发者

在任务进行中用 /btw 提了一个问题，得到有价值的回答，然后上下文切换，忘记保存。高认知负荷的工作状态让这件事很容易发生。

③
ADHD 倾向用户——受影响最深

/btw 功能发布时，Reddit 社区称其为"送给我们这些有 ADHD 脑子的 Claude Code 用户的礼物"。这群最喜爱 /btw 的人，也最容易在保存前关闭浮层。

02 — 过程

先梳理约束，
再谈设计。

在寻找解决方案之前，我先梳理了真实的约束——架构、API 和 UX 三个层面。每一个约束都改变了最终方向。

三个改变方案的约束

约束分析
架构 /btw 回答从设计上就不进入对话历史。
→ 任何插件都无法在关闭后捕获原始回答。
API Claude Code Hook 系统没有 /btw 专属生命周期事件。
→ 不存在 onBtwDismiss。最接近的是 UserPromptSubmit。
UX 任何修复方案都不能改变 /btw 的默认行为。
→ 增加默认路径的摩擦 = 比问题本身更糟。

默认临时，主动持久。

关键设计决策：命令命名

第一版实现使用的命令是 /btw-saver:save-btw——19 个字符，而 /btw 只有 4 个。显然是错的。我评估了两个方向：

选择 → 方向 A /btw:save 插件名改为 "btw"，带命名空间，9 个字符，可靠
放弃 → 方向 B /save-btw ~/.claude/skills/ standalone——未有文档支撑，不可验证

我选择了方向 A。方向 B 依赖一个无法在官方文档中确认的目录约定。发布一个诚实但稍欠优雅的方案，好过发布一个精美但不可靠的方案。

04 — 反思

下次我会
做哪些不同的选择。

01
先做用户研究，再动手构建

我对受影响用户群体的识别来自推断，而非访谈。对 Claude Code 重度用户做一轮快速访谈，要么能验证这个痛点，要么会发现大多数人其实并不在意——两种结果都有价值。

02
先做 Figma Mockup，再做插件

我在插件实现上花的时间多过设计提案本身。对于一个针对设计岗位的 Portfolio 作品，浮层改动的视觉稿会比可运行的 Node.js 代码更有说服力。顺序应该反过来。

03
早期验证插件 API 假设

我生成了一个安装路径（~/.claude/skills/），结果发现是未经文档记录、不可靠的。在写 README 之前先做一个快速技术验证，可以省掉整整一轮迭代。

这个项目展示了什么

在真实产品中识别 UX 缺陷并精确表述——Nielsen 映射、用户分群、根因与表象的区分
在真实约束下工作——架构、API 和 UX 约束——而不是在真空中设计
交付可运行的产物，而不只是一份提案
诚实面对不可行的方案和自己的过程失误
