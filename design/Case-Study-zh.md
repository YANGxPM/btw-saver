# 案例研究：btw-saver
## 修复 Claude Code /btw 功能中不可见的状态边界问题

**角色：** UX 设计师 + AI PM  
**类型：** 个人项目——用户研究、UX 设计、插件开发  
**时间：** 2026-05  
**交付物：** UX 改进提案、可运行的 Claude Code 插件、GitHub 开源发布

---

## 项目概述

Claude Code 的 `/btw` 命令允许开发者在不污染主对话上下文的情况下提问，是一个广受好评的功能。但当浮层被关闭后，回答会永久消失——而且消失之前没有任何提示。

我将这个问题定性为系统状态可见性的设计缺陷，向 Anthropic 提交了核心修复提案，并以插件形式完成了一个可运行的替代方案。

---

## 问题发现

这个问题是我在使用 Claude Code 时亲身遇到的。我用 `/btw` 提了一个问题，得到了有用的回答，按下 Escape——回答就消失了。没有警告，没有恢复路径。

我的第一反应是：*这是 bug 吗？* 在调查架构之后，我确认这是刻意的设计——但无论设计意图如何，这个时刻的用户体验是断裂的。

根本原因在于：**浮层的外观和交互感与普通 Claude 回答完全一致。** 没有任何视觉线索区分"临时内容"与"持久内容"。用户在回答消失之前，无法感知自己正处于一个不保存状态的临时上下文中。

这直接对应 **Nielsen 可用性启发式第一条：系统状态的可见性（Visibility of System Status）。**

---

## 受影响的用户群体

我识别出三类最可能真实受到影响的用户：

**Claude Code 新用户**——尚未理解 `/btw` 的临时性本质。对他们来说，每一条回答看起来都一样，没有"这条会消失"的心智模型。

**深度专注工作中的开发者**——在任务进行中用 `/btw` 提了一个问题，得到有价值的回答，然后上下文切换，忘记保存。高认知负荷的工作状态让这件事很容易发生。

**ADHD 倾向用户**——值得注意的是，`/btw` 功能发布时，Reddit 社区的反应包括"这是送给我们这些有 ADHD 脑子的 Claude Code 用户的礼物"。这个功能正是被最容易在关闭前忘记保存的人群所喜爱。

---

## 设计约束

在寻找解决方案之前，我先梳理了约束条件：

**架构约束：** `/btw` 回答从设计上就不进入对话历史。这意味着任何插件都无法在关闭后捕获原始回答——只能重新生成。

**插件 API 约束：** Claude Code 的 Hook 系统（截至 2026 年 5 月）没有 `/btw` 专属的生命周期事件，不存在 `onBtwDismiss` 这样的 Hook 可以拦截。现有最接近的 Hook 是 `UserPromptSubmit`，在用户发送下一条消息时触发。

**UX 约束：** 任何修复方案都不能改变 `/btw` 的默认行为。这个功能的价值正在于轻量和不打扰——任何增加默认路径摩擦的方案都会比问题本身更糟。

---

## 设计原则

> **默认临时，主动持久。**

目标不是让 `/btw` 变成持久存储。目标是在最关键的时刻——关闭之前——给用户一个清晰、低摩擦的主动保存选项。

---

## 解决方案：两个层次

### 第一层——核心修复提案（建议 Anthropic 实施）

理想方案需要对 Claude Code 浮层组件做一个小改动：在底部操作区加入保存按钮。

**现有底部操作区：**
```
[Space / Enter / Esc 关闭]
```

**改进后：**
```
[Space / Enter / Esc 关闭]    [S] 保存到日志
```

一个快捷键。将问答内容追加写入项目根目录下的 `.btw-log/btw-log.md`，短暂显示"已保存 ✓"确认提示后关闭浮层。

这个方案认知成本接近零，不改变默认行为，工程实现成本低。它在正确的层面解决问题——在浮层内部，在用户注意力最集中的时刻。

### 第二层——插件替代方案（已发布）

由于核心修复需要 Anthropic 介入，我构建了一个 Claude Code 插件作为最优替代方案。

**`/btw:save <问题>`**

用当前会话上下文重新回答 `/btw` 问题，并将结果连同时间戳保存到 `.btw-log/btw-log.md`。由于架构约束，回答可能与原始内容略有差异——重新生成是唯一可行的路径。

**`UserPromptSubmit` Hook**

检测用户的上一条消息是否为 `/btw`。在下一条消息时，静默向 Claude 的上下文注入一条软提醒："用户刚刚使用了 /btw——如果回答有价值，可以建议运行 /btw:save。" Claude 根据对话语境决定是否提示用户。非阻塞，不直接展示给用户。

---

## 关键设计决策：命令命名

第一版实现使用的命令是 `/btw-saver:save-btw`——19 个字符，而 `/btw` 只有 4 个。这显然是错的。

我评估了两个方向：

**方向 A：** 把插件名改为 `btw`，命令变成 `/btw:save`（9 个字符，带命名空间）

**方向 B：** 以 standalone skill 形式放在 `~/.claude/skills/`，命令变成 `/save-btw`（10 个字符，无命名空间）

最终我选择了**方向 A**作为可靠路径。方向 B 依赖一个我无法在官方文档中验证的目录约定——我选择不基于一个无法确认的假设来发布方案。

这个决策背后有一个我作为 AI PM 持有的原则：**发布一个诚实但稍欠优雅的方案，好过发布一个精美但不可靠的方案。**

---

## 方案权衡

| | 理想方案（保存按钮） | 本插件 |
|---|---|---|
| 触发时机 | 关闭前，一键完成 | 关闭后，运行 `/btw:save` |
| 回答还原度 | 精确 | 重新生成（可能略有差异） |
| 操作摩擦 | 接近零 | 低 |
| 需要修改核心代码 | 是 | 否 |
| 今天就能用 | 否 | 是 |

## 反思

这个项目从一个个人使用中的不爽出发，在不到一天内成为了一个产品案例研究。有几件事我会在下次做不同的选择：

**先做用户研究，再动手构建。** 我对受影响用户群体的识别来自推断，而非访谈。对 Claude Code 重度用户做一轮快速访谈，要么能验证这个痛点，要么会发现大多数人其实并不在意——两种结果都有价值。

**先做浮层 Mockup，再做插件。** 我在插件实现上花的时间多过设计提案本身。对于一个针对设计岗位的 Portfolio 作品，浮层改动的 Figma 视觉稿会比可运行的 Node.js 代码更有说服力。顺序应该反过来。

**早期验证插件 API 假设。** 我生成了一个安装路径（`~/.claude/skills/`），结果发现是未经文档记录、不可靠的。在写 README 之前先做一个快速技术验证，可以省掉整整一轮迭代。

## 这个项目展示了什么

- 在真实产品中识别 UX 缺陷并精确表述（Nielsen 映射、用户分群、根因与表象的区分）
- 在真实约束下工作——架构约束、API 约束、UX 约束——而不是在真空中设计
- 交付可运行的产物，而不只是一份提案
- 诚实面对不可行的方案和自己的过程失误
