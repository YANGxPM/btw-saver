UX Case Study · Claude Code · 2026

Fixing the invisible
state boundary in /btw

Claude Code's /btw command creates ephemeral side conversations. When dismissed, the answer is gone — permanently, silently. I identified the failure, proposed a core fix, and shipped a working plugin.

Role UX Designer · AI PM
Type Solo · Research + Design + Build
Timeline 2026-05
Deliverables UX Proposal · Plugin · GitHub
01 — PROBLEM

The answer disappears.
No warning. No recovery.

I discovered this firsthand. I asked a /btw question mid-session, got a useful answer, pressed Escape — and it was gone. My first instinct was: is this a bug?

After investigating the architecture, I confirmed it was intentional. But the user experience of that moment was broken regardless of intent.

Claude Code — user journey
user /btw do you like multi-model setups like deepseek + claude?
claude Multi-model setups are architecturally sound. DeepSeek
offers cost-efficiency; Claude excels at safety...
user [presses Escape]
answer gone — permanently, silently.

The root cause: the overlay looks and feels identical to a normal Claude response. There is no visual affordance distinguishing ephemeral content from persistent content. This maps directly to Nielsen Heuristic #1 — Visibility of System Status.

Who is affected

①
New Claude Code users

Haven't yet internalized /btw's ephemeral nature. Every response looks the same — no mental model for "this one disappears."

②
Deep-focus developers

Ask a /btw question mid-task, get a useful answer, context-switch before saving. High cognitive load makes this easy to miss.

③
ADHD-pattern users — most affected

When /btw launched, Reddit called it "a gift to us Claude Code homies that have the ADHD brain." This group — celebrated as /btw's biggest fans — is most likely to dismiss before saving.

02 — PROCESS

Constraints first.
Then design.

Before jumping to solutions, I mapped the real constraints — architectural, API, and UX. Each one shaped the final direction.

Three constraints that changed the solution

constraint analysis
ARCH /btw answers never enter conversation history by design.
→ No plugin can capture the exact answer after dismissal.
API Claude Code hooks have no /btw-specific lifecycle event.
→ No onBtwDismiss to intercept. Best option: UserPromptSubmit.
UX The fix must not change /btw's default behavior.
→ Adding friction to the default path = worse than the problem.

Ephemeral by default. Persistent by choice.

Key design decision: command naming

The first implementation used /btw-saver:save-btw — 19 characters vs /btw's 4. Clearly wrong. I evaluated two directions:

Chosen → Option A /btw:save rename plugin to "btw" → namespaced, 9 chars, reliable
Dropped → Option B /save-btw standalone skill at ~/.claude/skills/ — undocumented, unverifiable

I chose Option A. Option B depended on a directory convention I couldn't verify in official docs. Shipping something honest and slightly less elegant is better than shipping something polished that doesn't work.

03 — SOLUTION

Two layers.
One ships today.

Layer 1 — Core fix proposal for Anthropic

The ideal solution is a small change to the overlay component: a Save button in the footer. One keystroke. Zero change to default behavior.

04 — REFLECTION

What I'd do
differently.

01
User research before building

I identified affected users through inference, not interviews. A quick round with Claude Code power users would either validate the pain or reveal that most people don't actually care — both are useful signals.

02
Figma mockup before plugin

I spent more time on plugin implementation than on the design proposal. For a portfolio piece targeting a design role, the overlay Before/After mockup is more persuasive than working Node.js code. The order should have been reversed.

03
Validate API assumptions early

I generated an install path (~/.claude/skills/) that turned out to be undocumented and unreliable. A 10-minute technical spike before writing the README would have saved a full iteration cycle.

What this project demonstrates

Identifying a UX failure in a live product and articulating it precisely — Nielsen mapping, user segmentation, root cause vs. symptom
Operating within real constraints — architectural, API, and UX — rather than designing in a vacuum
Shipping a working artifact, not just a proposal
Being honest about what doesn't work — including my own process mistakes
